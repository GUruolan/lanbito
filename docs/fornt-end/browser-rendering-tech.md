# 浏览器架构与前端渲染技术要点

## 1. 浏览器多进程架构

现代浏览器（Chrome、Edge 等）采用**多进程架构**，各进程职责分离：

| 进程 | 职责 |
|------|------|
| **Browser 进程** | UI 渲染、标签页管理、网络请求调度、安全策略、存储协调 |
| **Renderer 进程** | 解析 HTML/CSS、执行 JS、构建 DOM、页面渲染 |
| **GPU 进程** | 图形加速、光栅化、最终像素上屏 |
| **Network 进程** | 网络请求处理（Chrome 后期版本独立） |
| **Utility 进程** | 音频、打印等辅助功能 |

**一个 Tab 涉及几个进程？**

- 最少 **1 个 Renderer 进程**（Tab 内所有内容同域）
- 最多 **多个 Renderer 进程**（存在跨域 iframe 时，每个跨域 iframe 独立进程）
- 始终共享 **1 个 Browser 进程** 和 **1 个 GPU 进程**

## 2. 一个 Tab 的线程模型

一个 Renderer 进程内包含多个线程：

| 线程 | 职责 |
|------|------|
| **主线程** | 解析 HTML/CSS、执行 JavaScript、构建 DOM、处理用户事件 |
| **合成器线程** | 图层合成、处理滚动和动画，独立于主线程 |
| **光栅化线程池** | 将绘制记录转为位图（通常多个线程） |
| **IO 线程** | 网络请求和资源加载 |
| **GC 线程** | V8 垃圾回收 |
| **Worker 线程** | 每个 Web Worker / Service Worker 独占一个线程 |

**关键特性**：合成器线程独立于主线程运行，因此即使 JS 阻塞主线程，页面滚动仍可流畅执行。

## 3. DOM 上屏流程

DOM 修改和上屏横跨多个线程/进程：

```
主线程（JS 执行）
  → 修改 DOM 结构
  → Style 计算
  → Layout（Reflow）
  → Paint（记录绘制指令）
  → 提交图层树 → 合成器线程

合成器线程（Renderer 进程）
  → 图层合成（Composite）
  → 生成绘制帧
  → 提交给 GPU 进程

GPU 进程
  → 光栅化（Rasterization）
  → 最终屏幕输出
```

- JavaScript 只能在**主线程**修改 DOM
- **上屏**（Composite + Raster + Display）由合成器线程和 GPU 进程完成
- 合成器线程不阻塞主线程，这是滚动流畅的关键

## 4. React 虚拟 DOM 与渲染机制

### 4.1 为什么不用 `requestIdleCallback`？

React 自己实现 **Scheduler** 包，原因：
- 浏览器兼容性差
- `timeRemaining()` 精度不够
- 可能因用户交互导致回调被延迟（饥饿问题）
- 无法满足优先级调度需求（高优先级任务打断低优先级任务）

React 实际使用 **`MessageChannel`** 创建宏任务：
- 速度比 `setTimeout(fn, 0)` 快（无 4ms 最小延迟）
- 跨浏览器一致
- 可精确控制时间切片

### 4.2 虚拟 DOM 在内存中 vs 真实 DOM 操作

**没有两个执行环境，没有线程切换。**

React 始终在**浏览器主线程**上运行，区分在于：

- **虚拟 DOM 构建和 Diff**：纯 JavaScript 对象操作，在内存中完成（同一线程内的 CPU 计算）
- **真实 DOM 操作**：Commit 阶段调用浏览器 C++ 接口（如 `createElement`、`appendChild`、`textContent`），同步执行
- **浏览器引擎接管**：Style → Layout → Paint → Composite，由 Blink/WebCore 底层处理

### 4.3 虚拟 DOM 的优势

| 优势 | 说明 |
|------|------|
| **批量更新** | 收集所有变更后一次性写入 DOM，减少重排重绘 |
| **声明式编程** | 只需描述"想要的状态"，无需手动追踪和操作具体 DOM 节点 |
| **跨平台抽象** | React Native 将虚拟 DOM 映射到原生 iOS/Android 组件 |
| **时间切片** | Fiber 架构可中断工作，让出主线程给高优先级任务（如用户输入） |
| **优先级调度** | 高优先级更新（如键盘输入）可打断低优先级更新（如列表渲染） |

### 4.4 Fiber 双缓冲与 Commit 阶段

- **Render 阶段**：构建虚拟 DOM 树、Diff 对比，可中断、可恢复
- **Commit 阶段**：同步执行真实 DOM 操作，不可中断

Fiber 的双缓冲技术（`current` 和 `workInProgress` 两棵树）确保内存中的比较不影响当前已渲染的 UI。

## 5. 总结

前端渲染的关键认知：

- 浏览器是多进程架构，但 JavaScript 始终在 Renderer 进程的**主线程**上执行
- DOM 修改和虚拟 DOM 计算都在同一根线程内，区别是**纯 JS 计算** vs **调用浏览器 C++ 接口**
- 虚拟 DOM 的优势不是"更快"，而是**可预测、可维护、可中断、可跨平台**
- 合成器线程的独立运行是页面流畅的基础，即使主线程被阻塞，滚动和动画仍可由合成器线程驱动
